Shah Tunnel 2.2.7

تغییرات اصلی:
- گزینه‌های ۱ تا ۷ رفتار قدیمی خود را حفظ می‌کنند.
- گزینه ۸ یک مسیر خارجی انتخاب‌شده با حامل احراز هویت‌شده TCP/TLS است.
- گزینه ۹ چهار انتقال قدیمی را با مسیرهای خارجی و مسیر فیزیکی مستقیم ترکیب می‌کند.
- مسیر Cloudflare WARP در گزینه ۸ و در فهرست گزینه ۹، از MASQUE دستگاهی استفاده می‌کند تا خروجی IPv4/IPv6 سرویس مقصد محلی (از جمله خروجی اینترنت کاربران VPN) نیز از WARP عبور کند.

اصلاح نسخه ۲٫۲٫۵:
- خطای «FIB table does not exist» در اولین راه‌اندازی WARP اصلاح شد؛ جدول جدید به‌عنوان جدول خالی شناسایی می‌شود و با افزودن مسیر فیزیکی ساخته می‌شود.
- بررسی جداگانهٔ IPv4 و IPv6 انجام می‌شود و خطاهای واقعی iproute2 همچنان متوقف‌کننده هستند.
- اگر route یا policy rule متعلق به سرویس دیگری از جدول رزروشده استفاده کند، Shah Tunnel آن را تغییر نمی‌دهد و با خطای ایمن متوقف می‌شود.

اصلاح نسخه ۲٫۲٫۷:
- خطای اجرای مجدد سرویس `shah-tunnel-warp-ssh-bypass` اصلاح شد. تشخیص Rule تکراری قبلاً پس از اولین فیلد نامرتبط متوقف می‌شد و Rule متعلق به خود شاه‌تونل را به‌اشتباه تداخل می‌دانست.
- اکنون تمام فیلدهای Rule بررسی می‌شوند؛ Rule یکسان موجود پذیرفته می‌شود، اما Rule متفاوت در همان اولویت همچنان رد می‌شود. تست بازگشتی این سناریو را با پاسخ شبیه‌سازی‌شدهٔ iproute2 بررسی می‌کند.

محافظت شبکه:
- پیش از فعال کردن WARP، Shah Tunnel مسیرهای پیش‌فرض فیزیکی IPv4/IPv6 را ثبت می‌کند.
- محافظ nftables پاسخ‌های پورت SSH را علامت‌گذاری می‌کند تا از مسیر فیزیکی VPS خارج شوند.
- سوکت‌های مستقیم/قدیمی Failover در گزینه ۹ با SO_MARK از مسیر فیزیکی خارج می‌شوند.
- سرویس systemd با CAP_NET_RAW و CAP_NET_ADMIN لازم برای SO_MARK اجرا می‌شود.
- گزینه‌های ۱ تا ۷ پیش از شروع، WARP مدیریت‌شده توسط Shah Tunnel را به Local Proxy برمی‌گردانند تا حامل پروتکل‌های قدیمی از WARP عبور نکند.
- اجرای هم‌زمان پروفایل Agent با سیاست WARP و پروفایل Agent بدون WARP جلوگیری می‌شود.

دامنه اثر مهم: وقتی گزینه ۸ با مسیر WARP فعال است یا گزینه ۹ دارای مسیر WARP است، WARP دستگاهی روی Agent فعال است. بنابراین سایر ترافیک‌های بدون علامت مسیریابی روی همان VPS نیز ممکن است از WARP عبور کنند. پاسخ‌های SSH و سوکت‌های مستقیم Failover مستثنا هستند. این نسخه مسیر خروجی را برای ترافیک سرویس مقصد نیز تغییر می‌دهد، اما ادعا نمی‌کند که فقط Xray و هیچ برنامه دیگری از WARP عبور می‌کند.

نصب‌کننده بسته رسمی WARP را روی Debian/Ubuntu پشتیبانی‌شده نصب می‌کند اما هنگام نصب اولیه آن را ثبت‌نام یا متصل نمی‌کند. اگر مخزن Cloudflare از VPS در دسترس نباشد، نصب هسته Shah Tunnel ادامه می‌یابد و مسیر WARP تا نصب موفق بسته در دسترس نخواهد بود.

برای اصلاح پروفایل Agent قدیمی، بعد از آپلود کامل همین نسخه به ریشه مخزن GitHub و نصب آن روی سرور خارج، فرمان زیر را اجرا کنید:
  ravanreverse repair-external

پروفایل Agent را انتخاب و Cloudflare WARP را انتخاب کنید. فرمان قبل از تغییر نسخه پشتیبان می‌سازد و توکن، Fingerprint، Hub، Mappingها و تعداد Laneها را حفظ می‌کند.

برای اجرای ZIP، فایل‌ها را استخراج و از پوشه اصلی با دسترسی root اجرا کنید:
  sudo bash S1T-START.sh

پس از انتشار همین فایل‌ها در شاخه main مخزن، نصب یک‌دستوره:
  bash <(curl -fsSL https://raw.githubusercontent.com/ShahNetLab/ShahTunnel/main/S1T-START.sh)

این ZIP به‌تنهایی فایل‌های مخزن GitHub را تغییر نمی‌دهد.


اصلاح ۲٫۲٫۶: پیش‌بررسی سیاست خروجی Agent پیش از گرفتن توکن و پیش از ذخیره اجرا می‌شود. اگر Agent قدیمیِ مستقیم فعال باشد، انتخاب WARP دستگاهی برای پروفایل جدید بدون ذخیرهٔ فایل جدید متوقف می‌شود؛ سرویس و خروجی کاربران تونل قبلی دست‌نخورده می‌ماند. اجرای هم‌زمان با خروجی‌های متفاوت روی یک VPS نیازمند جداسازی مستقل شبکه/Xray یا VPS جداست.
