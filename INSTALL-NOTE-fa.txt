شاه‌تونل 4.0.0
================

- اتصال Psiphon روی پورت عمومی Mapping: وقتی پورت کنترل Hub از مسیر Psiphon مسدود باشد، Agent فقط در مسیر Psiphon به Mapping عمومی پیش‌فرض TCP/443 Hub وصل می‌شود؛ این پورت از پورت کنترل مستقل است. ALPN اختصاصی shah-tunnel-control/1 در همان listener ترافیک کنترل را از TLS کاربران جدا می‌کند و دادهٔ عادی Mapping را بدون تغییر عبور می‌دهد؛ مسیر Direct و پورت کنترل اصلی دست‌نخورده می‌مانند. این قابلیت به Hub نسخه 3.0.3 یا جدیدتر و Agent نسخه 3.0.4 یا جدیدتر نیاز دارد.

- گزینه‌های 1 تا 7 در انتخاب‌گر انتقال همان رفتار و شماره‌گذاری قبلی را حفظ می‌کنند.
- مسیر خروجی سیستمی حذف‌شده در پروفایل‌های قدیمی عمداً به Direct تبدیل نمی‌شود؛ چنین Agentهایی باید دوباره با MASQUE یا Psiphon پیکربندی شوند.
- گزینه 8 به انتخاب‌گر انتقال اضافه شده است: Cloudflare WARP با MASQUE و پراکسی محلی WarpProxy (برای خروجی مستقل هر پروفایل) یا Psiphon از طریق SOCKS5.
- گزینه 9 ویزارد چهار انتقال داخلی را با Failover خروجی تطبیقی ترکیب می‌کند؛ این گزینه از گزینهٔ جداگانهٔ WARP در منوی اصلی مستقل است.
- Hub فقط انتقال‌های داخلی را می‌پذیرد؛ انتخاب MASQUE یا Psiphon در نقش Agent انجام می‌شود.
- در نسخه 3.0.8، هنگام ساخت Agent جدید با خروجی Psiphon، خروجی کاربران هم پیش از شروع سرویس به‌صورت خودکار آماده می‌شود: Inboundهای Mapping در Sidecar مجزا کپی می‌شوند؛ TCP و DNS از SOCKS5 محلی Psiphon عبور می‌کنند و UDP/شبکه ناشناخته به Blackhole می‌رود تا از مسیر Direct نشت نکند. گزینهٔ جداگانه‌ای در منوی مدیریت وجود ندارد. این مسیر UDP/QUIC و ICMP ping ندارد؛ پروفایل‌های قدیمی دست‌نخورده می‌مانند.
- Psiphon به‌صورت خودکار آماده می‌شود: هنگام ساخت Agent با خروجی Psiphon یا Adaptive، نصب‌کنندهٔ همراه پروژه ConsoleClient رسمی Psiphon را از سورس upstream ثابت‌شده برای معماری amd64/arm64 می‌سازد، نسخه و معماری ELF را بررسی می‌کند و در /usr/local/bin/psiphon-console-client نصب می‌کند. ShahTunnel سپس برای هر Agent فایل JSON خصوصی، دریافت فهرست سرور امضاشده، SOCKS5 یکتای 127.0.0.1 و پوشه داده مستقل تولید می‌کند؛ نیازی به باینری یا JSON دستی نیست. اولین استفاده به دسترسی اینترنت برای دریافت سورس رسمی GitHub و در صورت نیاز Go 1.26.1 از توزیع رسمی Go نیاز دارد. ConsoleClient فقط در حالت local SOCKS اجرا می‌شود؛ هیچ TUN یا مسیر پیش‌فرضی در سیستم ایجاد نمی‌کند. Laneهای TCP ارتباط Agent با Hub و در نسخه 3.0.8 خروجی TCP/DNS کاربران Xray از Psiphon استفاده می‌کنند؛ خروجی UDP کاربران مسدود می‌شود تا مستقیم خارج نشود. در حالت Adaptive، اگر Psiphon متصل نشود، مسیر Direct باقی می‌ماند. نصب‌کننده مسیر داده را در systemd مجاز می‌کند و ProtectSystem=strict را حفظ می‌کند.
- اصلاح Sandbox در Psiphon: `ListenInterface` خالی می‌ماند تا SOCKS5 روی loopback داخلی Psiphon bind شود؛ اما WebRTC ICE همچنان ممکن است برای کشف رابط‌های شبکه از `AF_NETLINK` استفاده کند. Unit و Drop-in نصب‌کننده این خانوادهٔ سوکت را مجاز می‌کنند و همچنان فقط `CAP_NET_BIND_SERVICE` دارند؛ `CAP_NET_ADMIN` داده نمی‌شود و Route/Interface تغییر نمی‌کند.
- برای WARP/MASQUE وضعیت Connected، پروتکل MASQUE و Listener محلی WarpProxy بررسی می‌شوند. خروجی کاربران یک پروفایل فقط با Local Proxy قابل جداسازی است؛ حالت System Tunnel به‌دلیل اعمال مسیریابی در سطح کل میزبان برای این قابلیت رد می‌شود. ShahTunnel هرگز Route سیستم را تغییر نمی‌دهد و WARP را خودکار connect/disconnect نمی‌کند.
- هنگام ساخت Agent و انتخاب WARP/MASQUE، اگر WarpProxy در دسترس نباشد ویزارد پیش از ایجاد پروفایل متوقف می‌شود. اگر پیش‌نیازها حاضر باشند، Sidecar مستقل Xray و مسیر DNS به‌صورت خودکار و پیش از شروع Agent اعمال می‌شوند. عملیات جداگانهٔ [9] در منوی اصلی مدیریت حذف شده است. Sidecar فقط Inboundهای همان پروفایل را روی Loopback کپی می‌کند؛ تنظیمات و سرویس X-UI تغییر یا restart نمی‌شوند و سایر پروفایل‌ها مستقل می‌مانند. DNS نیز با DoH و از همان WARP عبور می‌کند.
- منوی اصلی مدیریت فقط عملیات 1 تا 8 و خروج 0 را دارد؛ گزینهٔ 9 داخل ویزارد ساخت تونل همچنان All-protocol adaptive است.
- تصویر Network Flow و نشان‌های نسخه در این انتشار به 4.0.0 به‌روزرسانی شده‌اند.

نکتهٔ SSH:
فعال کردن WARP ممکن است مسیر پیش‌فرض سیستم را تغییر دهد. آن را از کنسول ارائه‌دهنده یا با دسترسی جایگزین آزمایش کنید؛ فقط با یک نشست SSH اقدام به تغییر default route نکنید.

تست‌ها شامل عبور نشست‌های TCP/TLS، WebSocket/TLS، HTTP/2 و HTTP/1.1، ساخت Sidecarهای ایزوله Xray، مسیریابی TCP/DNS از Psiphon، مسدودسازی fail-closed برای UDP، پراکسی SOCKS5 و WARP Local Proxy، failover مسیر خروجی، انتخاب Lane بر پایه RTT تازه (نمونه‌گیری ۵ ثانیه‌ای و اعتبار ۱۵ ثانیه‌ای)، تنظیم بافر Psiphon متناسب با RAM/CPU، Cache DNS و `go test -race`، `go vet` و build برای amd64/arm64 هستند. تست زنده Xray/Psiphon روی سرور واقعی به Xray فعال و تونل Psiphon متصل نیاز دارد.

نصب‌کننده سرویس فعال ShahTunnel را خودکار restart نمی‌کند تا نشست‌ها قطع نشوند. پس از آماده‌بودن برای وقفه کوتاه تونل، فقط سرویس مربوط به ShahTunnel را restart کنید؛ sshd دست‌کاری نمی‌شود.

روش انتشار و نصب:
- در GitHub فقط سورس، تست‌ها، مستندات و S1T-START.sh قرار می‌گیرد؛ هیچ باینری ShahTunnel را commit یا در Releases آپلود نکنید.
- دستور one-line بالا اسکریپت را از raw.githubusercontent.com دریافت می‌کند.
- اسکریپت سورس را از codeload.github.com/ShahNetLab/ShahTunnel شاخه main می‌گیرد، ابزار Go نسخه 1.26.1 را از توزیع رسمی Go با SHA-256 معتبر می‌کند و باینری را روی همان VPS می‌سازد.
- باینری نهایی فقط روی VPS در /usr/local/bin/ravanreverse نصب می‌شود.


نصب سریع از GitHub (Linux amd64/arm64 با systemd):
bash <(curl -fsSL https://raw.githubusercontent.com/ShahNetLab/ShahTunnel/main/S1T-START.sh)


## اصلاح اتصال Psiphon در پروفایل موجود

اگر ConsoleClient نصب شده اما پیش از ایجاد تونل خارج می‌شود، پس از اجرای نصب‌کنندهٔ جدید، اسکریپت نصب‌شدهٔ تعمیر را اجرا کنید: `sudo bash /usr/local/lib/shah-tunnel/repair-psiphon-profile.sh s`. این اسکریپت فقط همان Agent را متوقف/اجرا می‌کند، قبل از کار از فایل Psiphon نسخهٔ پشتیبان می‌گیرد و مجوز نوشتن پوشهٔ داده را فقط در صورت نیاز و فقط برای همان پروفایل اضافه می‌کند. باینری جدید هنگام شروع، شناسه‌های placeholder یا خالی و قالب قدیمی تک‌آدرس را تشخیص می‌دهد و کانفیگ را به قالب جدید RemoteServerListURLs و ObfuscatedServerListRootURLs مهاجرت می‌دهد؛ شناسه‌های معتبر سفارشی و منطقهٔ خروجی حفظ می‌شوند. اسکریپت تا ۱۰۰ ثانیه برای آماده‌شدن SOCKS5 محلی صبر می‌کند. اگر SOCKS5 آماده شود ولی تونل واقعی Psiphon یا Lane ارتباط Agent↔Hub هنوز وصل نشده باشد، وضعیت PENDING گزارش می‌شود و سرویس برای ادامهٔ تلاش‌ها روشن می‌ماند؛ موفقیت اتصال ادعا نمی‌شود. فقط اگر SOCKS5 محلی در مهلت تعیین‌شده آماده نشود، همان پروفایل متوقف می‌شود. پیام‌های تشخیصی Psiphon در Journal محلی فعال‌اند و ممکن است جزئیات حساس نشست/شبکه داشته باشند؛ آن‌ها را عمومی منتشر نکنید.

- شروع Psiphon: نسخه 3.0.8 پس از آماده‌شدن SOCKS5 محلی، فرایند ConsoleClient را به‌خاطر مهلت ثابت ۹۰ ثانیه نمی‌کشد. تا زمان اتصال واقعی Psiphon تلاش ادامه پیدا می‌کند؛ ویزارد وضعیت در انتظار را از اتصال موفق جدا نشان می‌دهد. گزارش‌های تشخیصی فقط در Journal محلی ثبت می‌شوند و ممکن است جزئیات شبکه داشته باشند.

- اصلاح نسخه 3.0.7: در حالت Psiphon، TCP/TLS و WebSocket/TLS از Public Mapping استفاده می‌کنند؛ HTTP/2 CONNECT و HTTP/1.1 CONNECT به‌ترتیب از Control Port+1 و Control Port+2 استفاده می‌کنند. آدرس Mapping دیگر مبنای محاسبه پورت‌های CONNECT نیست.

- اصلاح خودکار نسخه 3.0.7: مجوز `AF_NETLINK` در فایل‌های اصلی سرویس و Drop-in نصب‌کننده ثبت شده است تا هنگام نصب و ارتقا دیگر نیازی به ساخت دستی فایل `10-psiphon-netlink.conf` نباشد.

- اصلاح مهم ارتقا در نسخه 3.0.7: در نسخه‌های قبلی ممکن بود نصب‌کننده فایل Unit و Drop-in را اصلاح کند، اما فرایند فعال Agent با Sandbox قدیمی به کار ادامه دهد. اکنون نصب‌کننده پس از systemd daemon-reload دقیقاً فایل `/etc/systemd/system/ravanreverse@.service.d/10-psiphon-netlink.conf` با محتوای اصلاح دستی موفق را می‌سازد و فقط پروفایل‌های فعال Agent با خروجی Psiphon/Adaptive را restart می‌کند. Hub، مسیرهای Direct/WARP و پروفایل‌های نامرتبط restart نمی‌شوند.

بهینه‌سازی‌های 4.0.0 برای Psiphon:
- PING/PONG مسیرهای داخلی هر ۵ ثانیه سنجیده می‌شود؛ EWMA سریع‌تر است و نمونه‌های قدیمی‌تر از ۱۵ ثانیه از امتیاز انتخاب کنار گذاشته می‌شوند. این RTT مربوط به Lane ارتباط Hub↔Agent است، نه ICMP دستگاه کاربر.
- برای RAM کمتر از ۳ GiB، بافرهای محافظه‌کارانهٔ Psiphon حفظ می‌شوند؛ از ۳ GiB به بالا محدودیت Meek/Relay برای افزایش توان TCP برداشته می‌شود. محدودیت CPU فقط روی چند‌هسته‌ای‌ها برداشته می‌شود.
- Cache DNS در Sidecar Xray فعال است. UDP/QUIC و ICMP روی مسیر SOCKS5 سایفون همچنان پشتیبانی نمی‌شوند و fail-closed باقی می‌مانند.
- هیچ تضمینی برای کاهش RTT پایهٔ Psiphon وجود ندارد؛ محل و ازدحام سرور خروجی و مسیر شبکه تعیین‌کننده‌اند.
