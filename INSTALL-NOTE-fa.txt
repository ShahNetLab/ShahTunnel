شاه‌تونل 4.0.5
================

نکات این انتشار
---------------
- بهینه‌سازی 4.0.5 برای ۴۰ کاربر هم‌زمان: مقدار رسمی Psiphon `TunnelPoolSize` به‌صورت منابع‌محور تنظیم می‌شود؛ روی Agent با حداقل ۴ GiB RAM و ۲ CPU مقدار هدف ۸ تونل موازی است. این قابلیت محدودیت تک‌تونلی پیش‌فرض سایفون را کاهش می‌دهد، اما ظرفیت واقعی به VPS و شبکهٔ Psiphon وابسته است.
- برای مجموعهٔ کامل قابلیت‌ها، Hub و Agent هر دو باید نسخهٔ 4.0.5 را اجرا کنند.
- گزینه‌های خروجی Agent شامل Cloudflare WARP over MASQUE با WarpProxy/Local Proxy و Psiphon ConsoleClient از طریق SOCKS5 محلی است. WireGuard از گزینه‌های پروژه حذف شده است.
- انتخاب خروجی در زمان ساخت Agent اعمال می‌شود. WARP و Psiphon برای همان پروفایل Sidecar مستقل Xray می‌سازند؛ X-UI، فایل اصلی Xray، SSH، Routeهای میزبان و سایر پروفایل‌ها تغییر نمی‌کنند.
- Psiphon از ConsoleClient رسمی و SOCKS5 فقط روی Loopback استفاده می‌کند. برای هر Agent تنظیمات JSON خصوصی، پورت SOCKS5 مستقل و پوشه دادهٔ مستقل ایجاد می‌شود. هیچ TUN یا مسیر پیش‌فرضی در میزبان ایجاد نمی‌شود.
- خروجی Psiphon برای TCP و DNS همان Mapping از Sidecar مستقل Xray عبور می‌کند. UDP، QUIC و شبکه‌های ناشناخته به‌صورت fail-closed مسدود می‌شوند تا از مسیر مستقیم سرور خارج نشوند. ICMP ping از SOCKS5 عبور نمی‌کند.
- اتصال Agent به Hub در حالت Psiphon نیز از SOCKS5 همان پروفایل استفاده می‌کند. اگر پورت کنترل از این مسیر قابل دسترسی نباشد، Endpoint جایگزین Mapping عمومی TCP/443 با ALPN اختصاصی ShahTunnel استفاده می‌شود؛ ترافیک عادی Mapping بدون تغییر عبور می‌کند.
- آماده‌شدن Listener محلی SOCKS5 به‌تنهایی اتصال واقعی Psiphon محسوب نمی‌شود. اتصال واقعی Psiphon جداگانه بررسی می‌شود؛ آماده‌بودن Laneهای Agent نیز وضعیت جداگانه‌ای دارد و در صورت تأخیر، سرویس برای اتصال مجدد روشن می‌ماند.
- اصلاح راه‌اندازی Psiphon در Hotfix 4.0.5: ابتدا سرویس همان Agent اجرا و اتصال واقعی Psiphon بررسی می‌شود؛ بعد Sidecar مستقل Xray ساخته می‌شود و سرویس Agent فقط برای بارگذاری Mapping جدید همان پروفایل راه‌اندازی مجدد می‌شود. Listener SOCKS5 تا ۳۰ ثانیه برای آماده‌شدن فرصت دارد. اگر پروفایل 4.0.5 قبلاً ذخیره شده ولی به‌خاطر خطای `connection refused` خروجی Xray آن کامل نشده، گزینهٔ ۲ (Start a tunnel) آن پروفایل را به‌طور خودکار ترمیم می‌کند.
- در حالت WARP، اتصال MASQUE و Listener محلی WarpProxy بررسی می‌شوند. System Tunnel برای خروجی مستقل هر پروفایل پذیرفته نمی‌شود، چون مسیر آن در سطح میزبان است. ShahTunnel مسیر سیستم را تغییر نمی‌دهد و WARP را خودکار قطع یا وصل نمی‌کند.

بهینه‌سازی Psiphon در نسخهٔ 4.0.0
--------------------------------
- RTT داخلی Laneهای Hub↔Agent هر ۵ ثانیه با PING/PONG احرازشده اندازه‌گیری می‌شود؛ Hub فقط نمونه‌های تازه‌تر از ۱۵ ثانیه را در رتبه‌بندی مسیر لحاظ می‌کند و بار Streamهای فعال را هم در نظر می‌گیرد.
- برای RAM کمتر از ۳ GiB، محدودیت بافرهای Meek و Relay حفظ می‌شود؛ از ۳ GiB به بالا این محدودیت‌ها برداشته می‌شوند.
- اندازهٔ پنجرهٔ کانال SSH برای میزبان کم‌حافظه روی مقدار پیش‌فرض ۴ واحد (۱۲۸ KiB) باقی می‌ماند؛ روی میزبان دارای حداقل ۳ GiB RAM به ۱۶ واحد (۵۱۲ KiB) افزایش می‌یابد تا در مسیرهای با RTT زیاد توان TCP بهتر شود. محدودیت Threadهای CPU روی سرور تک‌هسته‌ای حفظ می‌شود. اندازهٔ پیش‌فرض Tunnel Pool سایفون تغییر نمی‌کند.
- Cache DNS در Sidecar Xray فعال است. این تغییرها برای توان TCP و انتخاب بهتر Lane هستند، نه تضمین کاهش پینگ پایهٔ مسیر Psiphon.
- RTT داخلی Hub↔Agent با پینگ سرتاسری نمایش‌داده‌شده در برنامهٔ موبایل یکی نیست. پینگ سرتاسری شامل مسیر دستگاه کاربر تا Hub، مسیر Agent و رلهٔ Psiphon تا مقصد است. عددی مثل ۶۳۵ ms باید قبل و بعد از نصب از همان کلاینت و به همان مقصد مقایسه شود.

امنیت و جداسازی
---------------
- Listener SOCKS5 سایفون فقط روی 127.0.0.1 قرار می‌گیرد.
- `CAP_NET_ADMIN` به سرویس داده نمی‌شود؛ `AF_NETLINK` فقط برای کشف رابط‌های شبکه مورد نیاز Psiphon مجاز است.
- UDP/QUIC در Sidecar سایفون مسدود است و به مسیر Direct fallback نمی‌کند.
- لاگ‌های تشخیصی Psiphon در Journal محلی ممکن است جزئیات شبکه و سرورها داشته باشند؛ آن‌ها را عمومی منتشر نکنید.
- اسکریپت تعمیر پروفایل فقط همان پروفایل Agent را هدف می‌گیرد و پیش از تغییر فایل Psiphon نسخهٔ پشتیبان می‌گیرد.

خروجی Tor برای Laneهای Agent و کاربران Xray
----------------------------
- گزینهٔ Tor در بخش External Egress شامل Snowflake و WebTunnel است؛ Psiphon از قبل موجود بود و حفظ شده است.
- نصب‌کننده بستهٔ رسمی Tor Expert Bundle نسخهٔ 16.0 را برای AMD64/ARM64 با SHA-256 ثابت‌شده بررسی می‌کند و Tor/Lyrebird را نصب می‌کند.
- Snowflake از Bridge پیش‌فرض مستندشده استفاده می‌کند؛ WebTunnel به Bridge شخصی/دریافت‌شده از Tor Bridges نیاز دارد.
- اتصال TCP بین Agent و Hub و همچنین TCP/DNS کاربران Inboundهای Xray همان Agent از SOCKS5 محلی Tor عبور می‌کند. UDP/QUIC و ICMP در مسیر کاربران پشتیبانی نمی‌شوند؛ UDP و شبکه‌های ناشناخته در Sidecar مسدود می‌شوند تا نشت مستقیم رخ ندهد.
- Sidecar Xray هر پروفایل جداست، فقط روی Loopback گوش می‌دهد و با توقف Agent متوقف می‌شود. فایل اصلی X-UI/Xray، Inboundهای دیگر، SSH و Routeهای میزبان تغییر نمی‌کنند.
- DNSTT و Slipstream در این نسخه نیستند؛ برای آن‌ها سرور DNS و دامنهٔ اختصاصی و توسعهٔ جریان اتصال دوطرفه در معماری لازم است. منوی غیرعملی اضافه نشده است.
- برای نصب بستهٔ Tor و دریافت Bridge، پروفایل را پیش از محدودیت یا خاموشی شبکه آماده کنید. این فناوری‌ها در نبود هرگونه مسیر ارتباطی باقی‌مانده اتصال را تضمین نمی‌کنند.

تست و محدودیت
-------------
در بستهٔ آماده‌شده، `go test ./...`، `go test -race ./...`، `go vet ./...`، بررسی Syntax اسکریپت‌ها و Build لینوکس AMD64/ARM64 با Go 1.23.2 اجرا و موفق شدند. نصب‌کننده همچنان Go 1.26.1 را با SHA-256 بررسی می‌کند. تست زندهٔ تأخیر و توان Psiphon به اتصال واقعی سرورها و کلاینت نیاز دارد و از محیط Build به‌تنهایی قابل تأیید نیست.

نصب سریع از GitHub (Linux amd64/arm64 با systemd)
--------------------------------------------------
bash <(curl -fsSL https://raw.githubusercontent.com/ShahNetLab/ShahTunnel/main/S1T-START.sh)

روش انتشار در GitHub
--------------------
1) ZIP را استخراج کنید.
2) تمام محتویات را در ریشهٔ مخزن `ShahNetLab/ShahTunnel` روی شاخهٔ `main` جایگزین کنید.
3) خود ZIP را در مخزن آپلود نکنید؛ فایل‌ها و پوشه‌ها را Commit و Push کنید.
4) روی هر دو سرور Hub و Agent نسخهٔ 4.0.5 را نصب کنید. برای جلوگیری از قطع ناخواستهٔ نشست‌ها، زمان نصب/راه‌اندازی مجدد را با وقفهٔ کوتاه تونل هماهنگ کنید.

نصب‌کننده سورس را از شاخهٔ `main` دریافت می‌کند، Go 1.26.1 را با SHA-256 معتبر می‌کند و باینری را روی همان VPS می‌سازد. باینری نهایی در `/usr/local/bin/ravanreverse` نصب می‌شود.
- گزینهٔ 9 با ۱۲ Lane مستقل، ترکیب‌های انتقال/خروجی را پخش و RTT هر Lane را با PING/PONG اندازه‌گیری می‌کند؛ Hub اتصال‌های جدید را به کم‌تأخیرترین Lane سالم با توجه به بار آن می‌فرستد. در قطع مسیر، Lane به گزینهٔ بعدی می‌رود. اتصال TCP فعال در میانهٔ کار قابل مهاجرت بی‌وقفه نیست.
- تشخیص Xray برای Sidecar دیگر به PID خروجی `ss -p` یا لینک‌های محدودشدهٔ `/proc/PID/cwd` و `/proc/PID/exe` وابسته نیست؛ از cmdline پردازش و WorkingDirectory/ExecStart واحد systemd استفاده می‌کند و در صورت چند تطبیق، به‌جای انتخاب تصادفی متوقف می‌شود.
