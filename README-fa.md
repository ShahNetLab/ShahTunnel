## تغییرات نسخه ۲٫۲٫۹ — خروجی واقعی WARP برای کاربران Xray

- گزینهٔ ۸ همچنان اتصال Agent به Hub را از SOCKS5 محلی WARP (`127.0.0.1:40000`) عبور می‌دهد.
- هنگام ساخت Agent می‌توان انتخاب کرد که ترافیک کاربران VPN هم از WARP خارج شود. در این حالت شاه‌تونل یک Xray جانبی مستقل از ورودی Xray فعلی می‌سازد؛ کاربران، UUIDها و تنظیمات TLS/Reality همان ورودی کپی می‌شوند و خروجی Xray جانبی به SOCKS5 WARP می‌رود.
- Xray اصلی پنل، فایل تنظیمات پنل، ورودی قبلی و سرویس‌های مستقیم متوقف یا ویرایش نمی‌شوند. نمونهٔ جانبی فقط روی loopback و یک پورت محلی جداگانه گوش می‌دهد.
- **برای کاربران WARP حتماً یک Hub جدا بسازید.** پورت کنترل و پورت عمومی کلاینت باید با Hub قبلی فرق داشته باشند. پیش‌فرض Wizard: پورت کنترل قبلی +۱۰، شناسهٔ Mapping برابر `warp` و پورت عمومی `0.0.0.0:8443`.
- کاربران قدیمی روی پورت قبلی می‌مانند و مستقیم خارج می‌شوند. فقط کلاینت‌هایی که به پورت عمومی جدید WARP (پیش‌فرض `8443`) وصل می‌شوند از مسیر WARP خارج خواهند شد.
- مقصد Agent باید یک ورودی Xray محلی روی `127.0.0.1` یا `::1` باشد. Wizard پردازش و فایل تنظیمات Xray فعال را پیدا می‌کند، کانفیگ جانبی را با همان باینری Xray تست می‌کند و اگر ورودی یکتا پیدا نشود، بدون دست‌کاری پنل متوقف می‌شود.
- اگر SOCKS5 محلی WARP برای IPv4 و IPv6 سالم نباشد، ساخت پروفایل متوقف می‌شود. مسیر پیش‌فرض VPS و SSH تغییر نمی‌کنند.
- این جداسازی برای جریان‌های TCP در Xray است؛ برای UDP/QUIC نباید بدون تست واقعی فرض کرد که Local Proxy کلاینت Cloudflare آن‌ها را نیز عبور می‌دهد.

## سازگاری و حفظ تونل‌های قبلی

پروفایل‌هایی که `target_egress: warp_xray` ندارند دقیقاً از مقصد و مسیر قبلی خود استفاده می‌کنند. Xray جانبی فایل تنظیمات فعال پنل را تغییر نمی‌دهد و Xray اصلی را Restart نمی‌کند. برای جلوگیری از مخلوط‌شدن نشست‌های مستقیم و WARP، پروفایل WARP باید Hub control port و public port جدا داشته باشد؛ تونل‌های قبلی روی پورت و مقصد قبلی باقی می‌مانند.

## قابلیت‌ها

- **چهار روش انتقال پیاده‌سازی‌شده:** TCP/TLS، ‏WebSocket/TLS، ‏HTTP/2 CONNECT و ‏HTTP/1.1 CONNECT/TLS.
- **بازیابی خودکار:** هر Lane مستقل با تأخیر افزایشی دوباره وصل می‌شود؛ گزینهٔ ۷ بین چهار انتقال قدیمی و گزینهٔ ۹ بین انتقال‌های قدیمی و مسیرهای خارجی جابه‌جا می‌شود. جریان TCP فعال از سوکت خراب بدون وقفه مهاجرت نمی‌کند و ممکن است دوباره برقرار شود.
- **امنیت:** TLS 1.3 در ارتباط خصوصی Hub↔Agent، احراز هویت توکن و تثبیت اثرانگشت SHA-256 گواهی.
- **هم‌زمانی:** دوازده lane مستقل به‌صورت پیش‌فرض، صف‌های محدود و انتخاب نشست با توجه به بار.
- **مدیریت:** منوی ترمینال، سرویس systemd، نمایش وضعیت و لاگ، نصب‌کننده و اسکریپت بررسی محلی.

## منوی انتقال

روی هر دو سمت Hub و Agent سیاست انتقال یکسان یا سازگار را انتخاب کنید. گزینه‌های ۱ تا ۷ معنی قدیمی خود را حفظ می‌کنند؛ گزینه‌های ۸ و ۹ مسیرهای خارجی را بدون جایگزین‌کردن انتقال‌های قبلی اضافه می‌کنند.

| گزینه | انتقال / راهبرد | عملکرد |
|---|---|---|
| `1` | TCP/TLS | جریان تونل روی اتصال TLS. |
| `2` | WebSocket/TLS | انتقال جریان در فریم‌های WebSocket داخل TLS. |
| `3` | HTTP/2 CONNECT | جریان CONNECT روی TLS و پورت TCP شمارهٔ کنترل + ۱. |
| `4` | HTTP/1.1 CONNECT/TLS | جریان CONNECT روی TLS و پورت TCP شمارهٔ کنترل + ۲. |
| `5` | HTTP CONNECT fallback | ابتدا HTTP/2 و در صورت شکست راه‌اندازی، HTTP/1.1 را امتحان می‌کند. |
| `6` | Automatic fallback | ابتدا TCP/TLS و سپس WebSocket/TLS. |
| `7` | FULL ADAPTIVE FAILOVER — قدیمی | همان چهار انتقال قدیمی را حفظ می‌کند و بین آن‌ها Failover انجام می‌دهد. |
| `8` | EXTERNAL TUNNEL | یک مسیر خارجی انتخاب‌شده روی Agent را با حامل احراز هویت‌شدهٔ TCP/TLS استفاده می‌کند. |
| `9` | FULL ADAPTIVE FAILOVER — همه | هر چهار انتقال قدیمی را روی مسیرهای خارجی پیکربندی‌شده و مسیر مستقیم امتحان می‌کند؛ ابتدا مسیر خارجی انتخاب‌شده و سپس مسیرهای جایگزین. |

### پورت‌های فایروال Hub

اگر پورت کنترل Hub برابر `9443` باشد:

- `9443/TCP`: ‏TCP/TLS و ‏WebSocket/TLS؛ همچنین برای گزینهٔ ۸ لازم است.
- `9444/TCP`: ‏HTTP/2 CONNECT در گزینه‌های ۳، ۵، ۷ و ۹.
- `9445/TCP`: ‏HTTP/1.1 CONNECT در گزینه‌های ۴، ۵، ۷ و ۹.

گزینهٔ ۸ فقط از حامل احراز هویت‌شدهٔ TCP/TLS استفاده می‌کند و به پورت کنترل نیاز دارد. گزینهٔ ۷ همان چهار انتقال داخلی قدیمی را نگه می‌دارد. گزینهٔ ۹ می‌تواند از هر چهار انتقال داخلی استفاده کند؛ بنابراین پورت کنترل، کنترل+۱ و کنترل+۲ باید در دسترس باشند. فقط پورت‌های لازم برای انتقال انتخاب‌شده را باز کنید.

### مسیرهای خارجی روی Agent

نصب‌کننده بستهٔ رسمی Cloudflare WARP را در سیستم‌های پشتیبانی‌شدهٔ Debian/Ubuntu دارای APT نصب می‌کند، اما هنگام نصب آن را ثبت‌نام یا متصل نمی‌کند. مسیرهای منوی Agent (انتخاب پیش‌فرض شمارهٔ ۲، Cloudflare WARP، است؛ نه Gateway آمادهٔ MASQUE):

- **MASQUE:** اتصال از طریق یک درگاه MASQUE محلی که به‌شکل SOCKS5 در دسترس است (پیش‌فرض `127.0.0.1:40001`). Wizard قبل از ذخیره، پاسخ واقعی SOCKS5 این درگاه را بررسی می‌کند. Shah Tunnel به‌تنهایی کلاینت مستقل MASQUE را اجرا نمی‌کند.
- **Cloudflare WARP:** از حالت Local Proxy کلاینت رسمی Cloudflare (`127.0.0.1:40000`) روی MASQUE به‌عنوان SOCKS5 استفاده می‌کند؛ فقط اتصال‌های همان Agent به Hub از WARP عبور می‌کنند. مسیر پیش‌فرض VPS تغییر نمی‌کند و تونل‌های دیگر، SSH و سرویس مقصد محلی دست‌نخورده می‌مانند. برای خروجی کاربران Xray، Wizard می‌تواند نمونهٔ جانبی مستقل بسازد و فقط همان ورودی را از WARP عبور دهد؛ Xray اصلی پنل دست‌نخورده می‌ماند.
- **WARP on WARP:** استفاده از یک نقطهٔ SOCKS5 دوم که جداگانه آماده شده است (پیش‌فرض `127.0.0.1:40002`). Shah Tunnel به‌تنهایی کلاینت دوم Cloudflare یا تونل دوم WARP ایجاد نمی‌کند.
- **Tor/Psiphon:** آدرس پراکسی SOCKS5 محلی را وارد کنید. پیش‌فرض Tor برابر `127.0.0.1:9050` و Psiphon برابر `127.0.0.1:1080` است؛ در صورت تفاوت، آدرس واقعی کلاینت را وارد کنید. نام مقصد توسط پراکسی Resolve می‌شود.

گزینهٔ ۷ همان حالت تطبیقی چهار انتقال قدیمی است. گزینهٔ ۸ مسیر خارجی انتخاب‌شده را با حامل TCP/TLS اجرا می‌کند و گزینهٔ ۹ چهار انتقال قدیمی را با مسیرهای خارجی ترکیب می‌کند. مسیرهای مبتنی بر SOCKS از جمله WARP فقط برای سوکت‌های همان Lane استفاده می‌شوند و مسیرهای مستقیم با اتصال عادی اجرا می‌شوند. هر Lane آخرین مسیر و انتقال موفق را نگه می‌دارد؛ جریان TCP فعال هنگام Failover بدون قطعی منتقل نمی‌شود و ممکن است دوباره وصل شود. Hub باید با گزینهٔ متناظر تنظیم شود.
**دامنهٔ اثر WARP:** نسخهٔ ۲٫۲٫۹ علاوه بر حامل Agent به Hub، امکان خروجی WARP برای کاربران Xray را با یک Xray جانبی مستقل فراهم می‌کند. حتماً Hub و پورت عمومی جدا بسازید؛ کلاینت‌های قدیمی روی مسیر مستقیم باقی می‌مانند.

### نصب WARP در شبکه‌های محدود

نصب‌کننده برای دریافت کلید رسمی Cloudflare از timeout محدود استفاده می‌کند. اگر `pkg.cloudflareclient.com` از شبکه VPS در دسترس نباشد، نصب WARP با پیام مشخص رد می‌شود و نصب هسته Shah Tunnel ادامه می‌یابد؛ هیچ routeای هنگام نصب اولیه تغییر نمی‌کند. در این حالت مسیر WARP تا نصب موفق کلاینت رسمی قابل استفاده نیست. برای پروفایل‌های جدید، نیازی به Ruleهای nftables، جدول مسیریابی یا تغییر Route سراسری نیست. اگر Agent قدیمی با WARP دستگاهی هنوز فعال باشد، ابتدا همان پروفایل را یک بار با نسخهٔ جدید Restart کنید؛ برنامه پیش از تغییر وضعیت تونل فعال قدیمی، این مورد را تشخیص می‌دهد و ایمن متوقف می‌شود.
