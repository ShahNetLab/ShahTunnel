## Network Flow | جریان شبکه

<div dir="rtl">

مسیر انتقال Hub به Agent و خروجی اینترنت اختیاری هر پروفایل مستقل از یکدیگرند: تونل، Mappingهای TCP را به مقصد محلی Agent می‌رساند؛ مسیر اختیاری Xray فقط Inbound انتخاب‌شده را از خروجی SOCKS5 WARP یا Psiphon همان پروفایل عبور می‌دهد.

</div>

```text
کاربر → پورت عمومی Hub → Laneهای احرازشده Agent → مقصد محلی Agent
Inbound انتخاب‌شده Xray → Sidecar محدود به Loopback → SOCKS5 خروجی WARP یا Psiphon → اینترنت
```

### خروجی خودکار کاربران از Psiphon

برای Agent جدیدی که هنگام ساخت، خروجی Psiphon را انتخاب می‌کند، Inboundهای Xray متناظر با Mappingها به‌صورت خودکار و پیش از شروع Agent در Sidecar مجزا و فقط روی `127.0.0.1` کپی می‌شوند. ترافیک TCP و DNS از SOCKS5 همان پروفایل عبور می‌کند. چون SOCKS5 محلی Psiphon یک پراکسی port-forward برای جریان TCP است و UDP را حمل نمی‌کند، UDP و هر نوع شبکهٔ ناشناخته در Sidecar به Blackhole می‌روند؛ بنابراین از خروج مستقیم UDP جلوگیری می‌شود، اما برنامه‌های UDP/QUIC و ICMP ping از این مسیر پشتیبانی نمی‌شوند. گزینهٔ جداگانه‌ای به منوی مدیریت اضافه نمی‌شود. پروفایل‌های قبلی دست‌نخورده باقی می‌مانند و این راه‌اندازی خودکار مخصوص Agentهای جدید است. این عملیات X-UI، کانفیگ اصلی Xray، سایر Inboundها، SSH و Routeهای میزبان را تغییر نمی‌دهد.

**بهینه‌سازی Psiphon در نسخه ۴٫۰٫۰:** اندازه‌گیری PING/PONG بین Hub و Agent هر ۵ ثانیه تازه می‌شود؛ میانگین‌گیری سریع‌تر (EWMA یک‌چهارم) است و فقط نمونه‌های تازه‌تر از ۱۵ ثانیه در انتخاب Lane نقش دارند. بار Streamهای فعال هم در امتیاز باقی می‌ماند و Cache DNS در Sidecar اختصاصی Xray فعال است. تنظیمات انتقال Psiphon متناسب با منابع میزبان است: زیر ۳ GiB RAM محدودیت محافظه‌کارانهٔ Meek/Relay و مقدار پیش‌فرض پنجرهٔ کانال SSH یعنی ۴ واحد (۱۲۸ KiB) حفظ می‌شود؛ از ۳ GiB به بالا محدودیت Meek/Relay برداشته و پنجرهٔ کانال SSH روی ۱۶ واحد (۵۱۲ KiB) تنظیم می‌شود تا توان TCP در مسیرهای دارای RTT زیاد بهتر شود. محدودیت Threadهای CPU فقط روی میزبان‌های حداقل دو هسته‌ای برداشته می‌شود و اندازهٔ پیش‌فرض Tunnel Pool سایفون حفظ می‌شود. این تغییرها برای انتخاب Lane بهتر و افزایش توان TCP هستند؛ زمان اتصال انتهابه‌انتهای برنامهٔ کاربر یا تأخیر فیزیکی مسیر Psiphon را تضمینی کاهش نمی‌دهند. SOCKS5 سایفون فقط TCP/DNS را حمل می‌کند؛ UDP/QUIC و ICMP ping پشتیبانی نمی‌شوند و به‌جای خروج مستقیم مسدود می‌شوند.
## انتقال‌های Hub↔Agent

در زمان ساخت تونل یک حالت را انتخاب کنید. تنظیمات Hub و Agent باید با هم سازگار باشند.

| گزینه ویزارد | حالت | عملکرد |
|:--:|---|---|
| `1` | TCP/TLS | جریان TLS بین Hub و Agent. |
| `2` | WebSocket/TLS | انتقال جریان تونل در فریم‌های باینری WebSocket روی TLS. |
| `3` | HTTP/2 CONNECT | انتقال CONNECT روی TLS و پورت کنترل + ۱. |
| `4` | HTTP/1.1 CONNECT/TLS | انتقال CONNECT روی TLS و پورت کنترل + ۲. |
| `5` | HTTP CONNECT fallback | ابتدا HTTP/2 و در صورت نیاز HTTP/1.1. |
| `6` | Automatic fallback | ابتدا TCP/TLS و سپس WebSocket/TLS. |
| `7` | Full Adaptive Failover | هر چهار انتقال؛ هر Lane آخرین انتقال موفق خود را ترجیح می‌دهد. |
| `8` | External egress | در Agent انتخاب Cloudflare MASQUE یا Psiphon/SOCKS5. |
| `9` | All-protocol adaptive | در Agent هر چهار انتقال را همراه با سنجش مسیرهای Hub از نظر دسترسی و RTT اجرا می‌کند؛ مسیر سالم با RTT کمتر اولویت می‌گیرد و پس از شکست مسیر، مسیر بعدی امتحان می‌شود. خروجی ترافیک کاربران Xray جداگانه بین Psiphon و WARP Local Proxy با Xray Observatory/leastPing انتخاب می‌شود. |

### اصلاح شناسایی Xray در نسخهٔ 4.0.2

در نصب‌هایی که Xray را `x-ui.service` با آرگومان نسبی مانند `-c bin/config.json` اجرا می‌کند، نسخهٔ 4.0.1 ممکن بود با فیلتر `ss` پردازش Xray را پیدا نکند و Sidecar قدیمی Psiphon را به حالت Adaptive ارتقا ندهد. نسخهٔ 4.0.2 تمام ردیف‌های TCP LISTEN را بررسی می‌کند و PID را بر اساس پورت واقعی Mapping پیدا می‌کند. در ارتقای گزینهٔ ۹، فقط Sidecar اختصاصی ShahTunnel همان پروفایل تغییر می‌کند؛ فایل اصلی X-UI، سرویس x-ui، SSH، Routeهای میزبان و Hub دست‌نخورده می‌مانند. نصب‌کننده فقط Agentهای فعال Psiphon/Adaptive را یک‌بار راه‌اندازی مجدد می‌کند.

### رفتار واقعی گزینهٔ ۹ در نسخهٔ ۴٫۰٫۲

- برای اتصال Agent به Hub، مسیرهای Direct، Psiphon و WARP/MASQUE فعال ابتدا با اتصال TCP واقعی تا مقصد Hub بررسی می‌شوند؛ مسیرهای قابل‌دسترسی بر اساس زمان اتصال مرتب می‌شوند. نتیجه برای ۴۵ ثانیه بین Laneها مشترک است و اگر یک مسیر تمام انتقال‌ها را شکست دهد، Cache پاک می‌شود تا مسیرها دوباره آزمایش شوند.
- در هر مسیر، هر چهار انتقال تطبیقی امتحان می‌شوند؛ پس از موفقیت، مسیر حفظ می‌شود و در قطع بعدی دوباره انتخاب انجام می‌شود. این سنجش، RTT اتصال تا Hub است و اندازه‌گیری سرعت دانلود/آپلود بر حسب Mbps نیست.
- برای ترافیک کاربران Xray، انتخاب جداگانه با Xray Observatory و `leastPing` بین SOCKS5 سایفون و WARP Local Proxy انجام می‌شود و هر ۲۰ ثانیه سلامت/تأخیر آن‌ها دوباره بررسی می‌شود. WARP باید در حالت **WarpProxy / Local Proxy** تنظیم شده باشد. حتی اگر Listener لحظهٔ شروع آماده نباشد، در صورت وجود تنظیم Loopback در `warp-cli settings`، مسیر به Xray معرفی می‌شود تا بعداً قابل انتخاب شود.
- خروج مستقیم سرور عمداً جزو خروجی ترافیک کاربران Xray نیست؛ اگر Psiphon و WARP هر دو از دسترس خارج شوند، TCP/DNS کاربران Fail-closed می‌شود و به IP عمومی VPS نشت نمی‌کند. UDP/QUIC و ICMP روی این مسیر پشتیبانی نمی‌شوند و مسدود می‌مانند. مسیر Direct فقط می‌تواند برای اتصال کنترل Agent به Hub انتخاب شود، نه خروج مستقیم کاربر.
- اگر WARP Local Proxy اصلاً پیکربندی نشده باشد، خروجی کاربران فعلاً فقط Psiphon است؛ گزینهٔ ۹ خودش WARP را نصب یا تنظیم نمی‌کند و Route سیستم یا SSH را تغییر نمی‌دهد.

### روش‌های خروجی Agent

| روش | پیش‌نیاز / مسیر |
|---|---|
| `Direct` | مسیر کنترل Agent→Hub از مسیر عادی سرور؛ به معنی خروج مستقیم ترافیک کاربران Xray نیست. |
| `WARP / MASQUE` | مسیر کنترل Agent→Hub از WARP فعال؛ خروج مستقل کاربران Xray فقط از WarpProxy / Local Proxy استفاده می‌کند و System Tunnel برای جداسازی پروفایل پذیرفته نمی‌شود. |
| `Psiphon / SOCKS5` | مسیر کنترل Agent→Hub و خروج Xray از SOCKS5 اختصاصی همان پروفایل؛ ConsoleClient رسمی و JSON خصوصی خودکار آماده می‌شود. |
| `Adaptive` | فقط برای مسیر کنترل Agent→Hub: MASQUE فعال، Psiphon و Direct را از نظر دسترسی و RTT بررسی می‌کند. انتخاب خروجی کاربران Xray جداگانه بین Psiphon و WARP Local Proxy است. |

### اتصال Psiphon از پورت عمومی ۴۴۳

اگر Psiphon به پورت کنترل Hub (برای نمونه `9448`) دسترسی نداشته باشد، Agent مسیر Psiphon را از نشانی Mapping عمومی Hub روی `443` عبور می‌دهد؛ مسیر Direct همچنان از پورت کنترل تنظیم‌شده استفاده می‌کند. مقدار پیش‌فرض Step 06 اکنون از پورت کنترل مستقل است و روی TCP/443 قرار می‌گیرد. Hub اتصال ShahTunnel را با ALPN اختصاصی `shah-tunnel-control/1` از ترافیک عادی TLS تشخیص می‌دهد و بایت‌های ClientHello کاربران عادی را بدون تغییر به Agent می‌فرستد. بنابراین نیازی به اشغال مجدد پورت ۴۴۳، تغییر X-UI، یا جابه‌جایی Mapping نیست.

برای استفاده از تمام قابلیت‌های ShahTunnel، هر دو سمت Hub و Agent باید نسخهٔ **4.0.2** را اجرا کنند. Mapping عمومی باید روی Hub فعال و از مسیر Psiphon قابل دسترسی باشد. در ویزارد Agent می‌توان نشانی جایگزین را تغییر داد؛ برای پروفایل‌های قدیمی که HubAddr آن‌ها روی `9443` است، مقدار `PsiphonHubAddr` هنگام بارگذاری به‌طور خودکار به همان IP روی `443` تبدیل می‌شود.

### راه‌اندازی خودکار Psiphon

با انتخاب `Psiphon / SOCKS5` یا مسیر خروجی تطبیقی در Agent، شاه‌تونل به‌صورت خودکار:

- ConsoleClient رسمی Psiphon را از نسخهٔ منبع ثابت‌شده، برای معماری `amd64` یا `arm64` می‌سازد.
- معماری و اجرای فایل باینری را پیش از نصب بررسی می‌کند.
- فایل JSON خصوصی هر Agent را با شناسه‌های عمومی کلاینت، آینه‌های فهرست سرور، کلید امضای فهرست، کلید امضای Server Entry و کلید Exchange می‌سازد.
- یک پورت SOCKS5 یکتا روی `127.0.0.1` و پوشهٔ دادهٔ مستقل اختصاص می‌دهد.
- دسترسی نوشتن systemd را فقط به پوشهٔ دادهٔ همان Agent محدود می‌کند.
- ConsoleClient را در حالت پراکسی محلی اجرا می‌کند. آماده‌شدن SOCKS5 محلی از اتصال واقعی Psiphon و از اتصال Lane به Hub جدا گزارش می‌شود. اگر SOCKS5 آماده شود اما مسیر هنوز کامل نشده باشد، سرویس فعال می‌ماند و وضعیت `PENDING` نشان داده می‌شود؛ اتصال موفق ادعا نمی‌شود. گزینهٔ `ListenInterface` ارسال نمی‌شود تا Psiphon از bind پیش‌فرض `127.0.0.1` استفاده کند و برای شناسایی اینترفیس به Netlink نیاز نداشته باشد. گزارش‌های تشخیصی فقط در Journal محلی ذخیره می‌شوند و می‌توانند اطلاعات حساس نشست/شبکه داشته باشند.

برای تعمیر پروفایلی که با تنظیمات قبلی Psiphon وصل نشده، از پوشهٔ پروژه اجرا کنید: `sudo bash repair-psiphon-profile.sh PROFILE`. این ابزار از JSON همان پروفایل نسخهٔ پشتیبان می‌گیرد و فقط سرویس `ravanreverse@PROFILE` را راه‌اندازی مجدد می‌کند. اگر SOCKS5 محلی آماده شود اما Psiphon یا Lane ارتباط با Hub هنوز متصل نشده باشد، وضعیت `PENDING` می‌دهد و سرویس را برای تلاش مجدد روشن می‌گذارد؛ فقط در صورت آماده‌نشدن SOCKS5، همان پروفایل را متوقف می‌کند.

نیازی به تهیهٔ دستی باینری یا JSON نیست. راه‌اندازی اولیه برای دریافت سورس رسمی و ابزار Go به دسترسی اینترنت نیاز دارد. هیچ TUN، مسیر پیش‌فرض سرور، SSH یا سرویس X-UI تغییر نمی‌کند. خروجی Psiphon در این پیاده‌سازی برای Laneهای TCP ارتباط Agent با Hub است و به معنی خروجی اینترنت کاربران Xray نیست.

> گزینه `9` فقط در ویزارد ساخت تونل وجود دارد و معنی آن **All-protocol adaptive** است. در منوی اصلی مدیریت دیگر عملیات جداگانهٔ WARP وجود ندارد؛ خروجی WARP هنگام ساخت Agent و انتخاب آن در بخش External Egress به‌صورت خودکار اعمال می‌شود.

## اعمال خودکار خروجی WARP هنگام ساخت Agent

- هنگام ساخت Agent، گزینهٔ Cloudflare WARP over MASQUE را انتخاب کنید.
- ShahTunnel پیش از ذخیره و شروع سرویس بررسی می‌کند که WARP با پروتکل MASQUE متصل است و Listener محلی **WarpProxy / Local Proxy** در دسترس است.
- سپس Sidecar مستقل Xray و مسیر DNS مبتنی بر WARP را فقط برای Mappingهای همان پروفایل آماده می‌کند.
- سایر پروفایل‌ها، Inboundهای دیگر، تنظیمات X-UI، SSH و مسیرهای میزبان تغییر نمی‌کنند.
- برای Agentهای موجود، این رفتار در زمان ساخت اعمال می‌شود؛ برای افزودن آن به یک Agent قدیمی، پروفایل Agent را دوباره با خروجی WARP بسازید. عملیات جداگانه‌ای در منوی مدیریت وجود ندارد.

**نکته مهم:** قابلیت خروجی اختصاصی هر پروفایل به **WarpProxy / Local Proxy در حالت MASQUE** نیاز دارد. حالت **System Tunnel** به‌دلیل اعمال مسیر در سطح کل سرور برای جداسازی یک پروفایل پذیرفته نمی‌شود. اگر Local Proxy فعال یا قابل دسترسی نباشد، ویزارد با پیام خطا متوقف می‌شود؛ ShahTunnel مسیر را بی‌صدا به Direct تغییر نمی‌دهد و Route میزبان را هم دست‌کاری نمی‌کند.

## مدیریت روزمره

`sudo shah-tunnel menu` منوی مدیریت را باز می‌کند. عملیات روی پروفایل انتخاب‌شده انجام می‌شود:

| گزینه منو | عملکرد |
|:--:|---|
| `1` | ساخت پروفایل جدید Hub، Agent یا Relay. |
| `2` | شروع تونل انتخاب‌شده. |
| `3` | توقف تونل انتخاب‌شده. |
| `4` | راه‌اندازی مجدد تونل انتخاب‌شده. |
| `5` | نمایش وضعیت و لاگ‌های اخیر. |
| `6` | تنظیم Restart زمان‌بندی‌شده تونل‌های فعال. |
| `7` | حذف فقط یک پروفایل انتخاب‌شده. |
| `8` | حذف کامل ShahTunnel. |

دستورهای کاربردی:

## امنیت

- توکن Hub و اثر انگشت گواهی را محرمانه نگه دارید. Agent باید دقیقاً از مقادیر تولیدشده در Hub استفاده کند.
- در فایروال Hub فقط پورت کنترل/CONNECT انتخاب‌شده و پورت‌های عمومی Mapping موردنیاز را باز کنید.
- توکن، کلید خصوصی، فایل کامل تنظیمات یا لاگ بدون حذف اطلاعات حساس را در Issue یا تصویر عمومی منتشر نکنید.
- Sidecar اختصاصی WARP برای Inbound کپی‌شده روی Loopback گوش می‌دهد و جایگزین سرویس اصلی Xray تحت مدیریت X-UI نمی‌شود.
- ShahTunnel را فقط روی سرورها و سرویس‌هایی استفاده کنید که مالک آن هستید یا مجوز مدیریتشان را دارید. [سیاست امنیتی](SECURITY.md).

## نصب

ShahTunnel از معماری **Hub / Agent** استفاده می‌کند. برنامه را روی سرور Hub و هر Agent نصب کنید. در صورت نیاز، یک سرور سوم نیز می‌تواند نقش Relay داشته باشد.

**پیش‌نیازها:** لینوکس `amd64` یا `arm64`، سرویس `systemd` و دسترسی root. نصب‌کننده ابزار Go نسخهٔ 1.26.1 را دریافت و با SHA-256 بررسی می‌کند، سپس باینری لینوکس را روی همان سرور می‌سازد.

**۱. نصب روی هر سرور**

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/ShahNetLab/ShahTunnel/main/S1T-START.sh)
```

<div dir="rtl">

پس از نصب، منوی مدیریت باز می‌شود. برای ورود دوباره:

</div>

```bash
sudo shah-tunnel menu
```

<div dir="rtl">

**۲. ساخت Hub**

1. گزینه ساخت تونل جدید را انتخاب کنید و نقش **HUB** را بزنید.
2. پورت کنترل را تعیین کنید (پیش‌فرض `0.0.0.0:9443`) و انتقال مورد قبول Hub را انتخاب کنید.
3. نگاشت پورت‌های عمومی را بسازید. برای هر نگاشت یک شناسه مانند `main` یا `web` تعیین کنید.
4. **توکن Agent** و **اثر انگشت SHA-256 گواهی** را ذخیره کنید؛ Agent باید دقیقاً از همین دو مقدار استفاده کند.

**۳. ساخت Agent**

1. روی سرور مقصد، تونل جدید بسازید و نقش **AGENT** را انتخاب کنید.
2. آدرس Hub و پورت کنترل را وارد کنید و انتقال سازگار با Hub را برگزینید.
3. توکن و اثر انگشت گواهی Hub را وارد کنید.
4. همان شناسه‌های Mapping را بسازید و مقصد محلی هرکدام را وارد کنید؛ برای نمونه `127.0.0.1:443`.
5. پروفایل را ذخیره کنید. ShahTunnel سرویس مستقل آن را فعال می‌کند و Laneهای قطع‌شده را به‌صورت خودکار دوباره متصل می‌کند.

**۴. فایروال:** فقط پورت‌های لازم را باز کنید. Hub به پورت کنترل انتخاب‌شده، پورت CONNECT در صورت نیاز (`کنترل + ۱` برای HTTP/2 یا `کنترل + ۲` برای HTTP/1.1) و پورت‌های عمومی Mapping نیاز دارد. Agent اتصال خروجی را به Hub برقرار می‌کند و مقصدهای محلی در سمت Agent هستند.

</div>

## عیب‌یابی

</div>

| مشکل | اولین بررسی |
|---|---|
| Agent متصل نمی‌شود | آدرس Hub، توکن، اثر انگشت گواهی، سازگاری حالت انتقال و پورت‌های فایروال را بررسی کنید. |
| HTTP/2 یا HTTP/1.1 CONNECT کار نمی‌کند | پورت TCP اضافه Hub را بررسی کنید (`کنترل + ۱` یا `کنترل + ۲`). |
| Mapping ترافیک را عبور نمی‌دهد | شناسه Mapping در Hub و Agent و دسترسی به مقصد محلی Agent را بررسی کنید. |
| خروجی WARP فعال نمی‌شود | قبل از ساخت Agent بررسی کنید WARP با MASQUE متصل است و `warp-cli settings` یک Listener محلی `WarpProxy` قابل دسترسی نشان می‌دهد. حالت System Tunnel برای جداسازی هر پروفایل پذیرفته نیست. |
| DNS گوگل/یوتیوب روی WARP مستقل مشکل دارد | وضعیت سرویس `shah-tunnel-xray-warp-<profile>.service` و لاگ‌های همان Sidecar را ببینید؛ مسیرهای میزبان را تغییر ندهید. |

## رفتار و بهینه‌سازی Psiphon در نسخهٔ ۴٫۰٫۰

- آماده‌شدن Listener محلی SOCKS5 به‌تنهایی به معنی اتصال واقعی Psiphon نیست. سرویس Agent روشن می‌ماند تا ConsoleClient تلاش مجدد کند؛ ویزارد فقط پس از برقراری تونل واقعی و آماده‌شدن Laneها، اتصال را موفق اعلام می‌کند.
- ترافیک TCP و DNS ورودی‌های Xray همان پروفایل از SOCKS5 محلی Psiphon عبور می‌کند. UDP، QUIC و نوع‌های ناشناختهٔ شبکه در Sidecar مستقل مسدود می‌شوند و به مسیر مستقیم سرور برنمی‌گردند. این مسیر SOCKS5، ICMP ping را حمل نمی‌کند.
- Psiphon فقط در حالت Local SOCKS اجرا می‌شود. ShahTunnel دستگاه TUN نمی‌سازد، مسیر پیش‌فرض میزبان را تغییر نمی‌دهد، `CAP_NET_ADMIN` نمی‌دهد و سرویس Xray تحت مدیریت X-UI را تغییر نمی‌دهد.
- RTT داخلی Laneهای Hub↔Agent با PING/PONG احرازشده هر ۵ ثانیه اندازه‌گیری می‌شود. Hub انتخاب مسیر را بر اساس RTT تازه و بار جریان‌های فعال انجام می‌دهد؛ نمونه‌های قدیمی‌تر از ۱۵ ثانیه از رتبه‌بندی کنار می‌روند. این عدد با تأخیر سرتاسری‌ای که برنامهٔ کلاینت نمایش می‌دهد یکسان نیست.
- روی میزبان‌های دارای کمتر از ۳ GiB RAM، محدودیت بافرهای Psiphon حفظ می‌شود. از ۳ GiB به بالا، محدودیت بافر Meek و Relay برداشته و پنجرهٔ کانال SSH روی ۱۶ واحد (۵۱۲ KiB) تنظیم می‌شود؛ میزبان کم‌حافظه مقدار پیش‌فرض مستند ۴ واحد (۱۲۸ KiB) را نگه می‌دارد. محدودیت Thread روی میزبان تک‌هسته‌ای فعال می‌ماند و اندازهٔ پیش‌فرض Tunnel Pool سایفون تغییر نمی‌کند.
- این تنظیمات برای افزایش توان TCP و واکنش سریع‌تر انتخاب Lane هستند؛ تأخیر فیزیکی مسیر کاربر تا Hub، رلهٔ Psiphon و مقصد را حذف نمی‌کنند. عددی مثل ۶۳۵ میلی‌ثانیه باید قبل و بعد از نصب از سمت کلاینت و در شرایط مشابه اندازه‌گیری شود؛ کاهش عدد مشخصی تضمین‌شدنی نیست.

برای مجموعهٔ کامل قابلیت‌ها، هر دو سرور Hub و Agent را روی نسخهٔ 4.0.2 نگه دارید. شماره‌های نسخهٔ تاریخی فقط در کد مهاجرت و تعمیر باقی می‌مانند تا نصب‌های قبلی شناسایی شوند؛ آن‌ها نسخهٔ اجرایی جداگانهٔ فعلی نیستند.
