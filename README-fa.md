## قابلیت‌ها

- **چهار روش انتقال پیاده‌سازی‌شده:** TCP/TLS، ‏WebSocket/TLS، ‏HTTP/2 CONNECT و ‏HTTP/1.1 CONNECT/TLS.
- **بازیابی تطبیقی:** گزینهٔ ۷ همان سیاست قدیمی چهار انتقال داخلی را حفظ می‌کند. گزینهٔ ۹ کانال‌های مستقل را بین چهار ترکیب انتقال داخلی/مسیر مستقیم و هر مسیر خارجی پیکربندی‌شده روی Agent تقسیم می‌کند تا مسیرهای سالم هم‌زمان فعال باشند. با ۱۲ کانال پیش‌فرض، چهار انتقال قدیمی به‌علاوهٔ حداکثر شش مسیر خارجی هرکدام می‌توانند کانال فعال داشته باشند. اگر مسیر یک Lane قطع شود، همان Lane گزینه‌های باقی‌مانده را امتحان می‌کند و با تأخیر افزایشی دوباره وصل می‌شود. جریان TCP فعال پس از خرابی سوکت باید دوباره برقرار شود و مهاجرت بی‌وقفهٔ نشست موجود تضمین نمی‌شود.
- **امنیت:** TLS 1.3 در ارتباط خصوصی Hub↔Agent، احراز هویت توکن و تثبیت اثرانگشت SHA-256 گواهی.
- **هم‌زمانی:** دوازده lane مستقل به‌صورت پیش‌فرض، صف‌های محدود و انتخاب نشست با توجه به بار.
- **مدیریت:** منوی ترمینال، سرویس systemd، نمایش وضعیت و لاگ، نصب‌کننده و اسکریپت بررسی محلی.

## منوی انتقال

روی هر دو سمت Hub و Agent گزینهٔ سازگار را انتخاب کنید.

| گزینه | انتقال / راهبرد | عملکرد |
|---|---|---|
| `1` | TCP/TLS | جریان رمزگذاری‌شده با TLS. |
| `2` | WebSocket/TLS | جریان تونل در فریم‌های باینری WebSocket روی TLS. |
| `3` | HTTP/2 CONNECT | جریان CONNECT روی TLS و پورت کنترل + ۱. |
| `4` | HTTP/1.1 CONNECT/TLS | جریان CONNECT روی TLS و پورت کنترل + ۲. |
| `5` | HTTP CONNECT fallback | ابتدا HTTP/2 و در صورت شکست راه‌اندازی، HTTP/1.1. |
| `6` | Automatic fallback | ابتدا TCP/TLS و سپس WebSocket/TLS. |
| `7` | **FULL ADAPTIVE FAILOVER — قدیمی** | همان رفتار قبلی: فقط چهار انتقال داخلی TCP/TLS، ‏WebSocket/TLS، ‏HTTP/2 CONNECT و ‏HTTP/1.1 CONNECT؛ هیچ مسیر خارجی جدیدی به این گزینه اضافه نمی‌شود. |
| `8` | **NEW TUNNEL PROTOCOLS** | فقط یک مسیر خارجی آماده‌شده روی Agent: ‏MASQUE، ‏Cloudflare WARP، ‏WARP on WARP، ‏Tor، ‏Psiphon یا Backhaul؛ Carrier احراز هویت‌شده تا Hub از نوع TCP/TLS است. |
| `9` | **FULL ADAPTIVE FAILOVER — قدیمی + جدید** | چهار انتقال داخلی به‌همراه تمام مسیرهای خارجی پیکربندی‌شده روی Agent. هر Lane پس از خرابی اتصال، گزینهٔ بعدی را امتحان و دوباره متصل می‌شود؛ مسیر مستقیم سیستم‌عامل نیز در فهرست تلاش‌هاست. |

Hub تعیین می‌کند چه Carrier/انتقالی را قبول کند. کلاینت‌ها و مسیرهای خارجی روی Agent تنظیم می‌شوند. گزینه‌های ۷ تا ۹ باید در هر دو سمت با هم سازگار انتخاب شوند.

**سازگاری ارتقا:** پروفایل‌های قبلی با مقدار `agent_external_tcp` همچنان از همان مسیر خارجی انتخاب‌شده استفاده می‌کنند (اکنون گزینهٔ ۸). پروفایل‌های `full_adaptive` نیز رفتار ترکیبی قبلی خود را حفظ می‌کنند (اکنون گزینهٔ ۹). نصب‌کننده فایل‌های پروفایل موجود را بازنویسی یا حذف نمی‌کند.
### پورت‌های فایروال Hub

اگر پورت کنترل Hub برابر `9443` باشد:

- `9443/TCP`: مسیرهای TCP/TLS و WebSocket/TLS.
- `9444/TCP`: ‏HTTP/2 CONNECT در گزینه‌های ۳، ۵، ۷ و ۹.
- `9445/TCP`: ‏HTTP/1.1 CONNECT در گزینه‌های ۴، ۵، ۷ و ۹.

فقط پورت‌های لازم برای گزینهٔ انتخاب‌شده را باز کنید. گزینهٔ ۸ فقط به پورت کنترل نیاز دارد؛ گزینه‌های ۷ و ۹ برای استفاده از هر چهار انتقال داخلی به پورت کنترل، کنترل+۱ و کنترل+۲ نیاز دارند.

### مسیرهای خارجی روی Agent

مسیرهای خارجی روی Agent تنظیم می‌شوند. نصب‌کنندهٔ اصلی Shah Tunnel در Ubuntu/Debian بستهٔ رسمی Cloudflare WARP را خودکار نصب و پروتکل آن را روی MASQUE تنظیم می‌کند. ثبت‌نام و اتصال اولیه فقط پس از تأیید تعاملی شرایط استفاده و حریم خصوصی Cloudflare انجام می‌شود. کلاینت‌های Tor، Psiphon و Backhaul و همچنین مسیر تو‌در‌توی WARP on WARP باید جداگانه توسط مدیر Agent آماده شوند. در Wizard سمت Agent مسیرهای آماده را اضافه کنید:

- **MASQUE:** از مسیر یا رابط شبکه‌ای که قبلاً روی Agent آماده شده استفاده می‌کند؛ این مسیر می‌تواند رابط Cloudflare WARP با پروتکل MASQUE یا یک مسیر MASQUE دیگر باشد.
- **Cloudflare WARP / WARP on WARP:** وضعیت `warp-cli status` باید `Connected` و `Network: healthy` باشد؛ مسیر WARP قطع‌شده رد می‌شود تا ترافیک ناخواسته از مسیر معمولی خارج نشود. نصب‌کننده پروتکل کلاینت Cloudflare WARP را روی MASQUE قرار می‌دهد.
- **WARP on WARP:** مسیر یا رابط تو‌در‌توی WARP باید از قبل روی Agent آماده شده باشد؛ انتخاب این مورد به‌تنهایی حساب یا تونل مستقل WARP دوم ایجاد نمی‌کند.
- **Tor و Psiphon:** آدرس SOCKS5 محلی کلاینت را وارد کنید (پیش‌فرض Tor برابر `127.0.0.1:9050` است؛ برای Psiphon باید Endpoint واقعی همان نصب را وارد کنید). اتصال Hub از SOCKS5 عبور می‌کند و DNS نام میزبان به پراکسی سپرده می‌شود.
- **Backhaul:** آدرس Local raw-TCP forward کلاینت Backhaul را وارد کنید. گزینهٔ ۸ فقط Forward پورت کنترل را لازم دارد؛ گزینهٔ ۹ برای استفاده از HTTP/2 و HTTP/1.1 به Forwardهای کنترل+۱ و کنترل+۲ هم نیاز دارد.

گزینهٔ ۷ عمداً از روش‌های خارجی جداست و همان چهار انتقال قدیمی را حفظ می‌کند. گزینهٔ ۸ فقط یک مسیر خارجی انتخاب‌شده را با Carrier ‏TCP/TLS به کار می‌گیرد. گزینهٔ ۹ کانال‌ها را بین چهار انتقال داخلی قدیمی و تمام مسیرهای خارجی پیکربندی‌شده تقسیم می‌کند تا در صورت کافی بودن تعداد کانال‌ها، مسیرهای سالم هم‌زمان فعال باشند. با قطع هر مسیر، همان Lane گزینه‌های بعدی را امتحان و دوباره متصل می‌شود؛ جریان TCP فعال بدون برقراری مجدد به سوکت دیگری منتقل نمی‌شود. Hub سیاست پذیرش انتقال‌ها را کنترل می‌کند و آماده‌سازی کلاینت خارجی بر عهدهٔ مدیر Agent است.

## مدیریت چند تانل و کارایی آپلود

- هر بار گزینهٔ «ساخت تانل» یک نام مستقل می‌گیرد و تنظیمات آن در فایل جداگانه ذخیره می‌شود؛ ساخت تانل جدید، تانل‌های قبلی را بازنویسی یا حذف نمی‌کند.
- هر پروفایل یک سرویس systemd مستقل دارد. گزینه‌های شروع، توقف، راه‌اندازی مجدد و وضعیت، ابتدا نام تانل را می‌پرسند.
- در منوی مدیریت تانل، گزینهٔ حذف یک پروفایل فقط همان تانل انتخاب‌شده را حذف می‌کند و حذف کامل برنامه همهٔ تانل‌ها را پاک می‌کند.
- پنجرهٔ ارسال هر جریان به ۶۴ فریم تا سقف ۶۴ کیلوبایت افزایش یافته است (حداکثر حدود ۴ مگابایت دادهٔ درحال‌پرواز برای هر جریان)، درحالی‌که صف خروجی هر اتصال محدودتر شده تا تأخیر صف و معطلی جریان‌های دیگر کمتر شود. روی کرنل‌های لینوکسِ دارای BBR، برنامه تلاش می‌کند الگوریتم BBR را فقط روی سوکت TCP تونل فعال کند؛ اگر کرنل پشتیبانی نکند، الگوریتم پیش‌فرض دست‌نخورده می‌ماند. این تغییرها می‌توانند محدودیت پنجره در مسیرهای با RTT بالا و تأخیر زیر بار را کاهش دهند؛ اما سرعت واقعی به پهنای‌باند، پکت‌لاس، ازدحام، qdisc کرنل و محدودیت اپراتور وابسته است. اشباع کامل لینک بالادست بدون تعیین سقف نرخ متناسب با ظرفیت واقعی شبکه، با تغییر نرم‌افزار به‌تنهایی قابل تضمین نیست.

## استفادهٔ مسئولانه و حریم خصوصی

ShahTunnel یک رلهٔ عمومی TCP است. آن را فقط برای سرورها و سرویس‌هایی پیکربندی کنید که مالک آن‌ها هستید یا مجوز صریح مدیریتشان را دارید. از آن برای دسترسی بدون مجوز به سامانه‌های اشخاص ثالث، انتقال ترافیک آزاردهنده یا مختل‌کردن سرویس‌ها استفاده نکنید. مسئولیت مقصدها و ترافیکی که عبور می‌دهید با مدیر سامانه است.

بخش نمایش اطلاعات سرور ممکن است برای تشخیص IPv4 عمومی و کشور سرور، درخواست HTTPS به سرویس‌های عمومی تشخیص IP و GeoIP از جمله ipify، icanhazip، checkip.amazonaws.com، ipinfo.io، ip.sb، ipapi.co و ipwho.is بفرستد. این سرویس‌ها می‌توانند IP عمومی سرور و فرادادهٔ درخواست را ببینند؛ درخواست‌های GeoIP شامل توکن تونل یا محتوای ترافیک تونل نیستند.

برای سازگاری هنگام ارتقا، نام واحد systemd و مسیر تنظیمات هنوز نام‌های قدیمی `ravanreverse.service` و `/etc/ravanreverse` را دارند؛ نصب‌کننده فرمان `shah-tunnel` را نیز به‌صورت symlink فراهم می‌کند. این‌ها نام‌های محلی برای سازگاری‌اند، نه مقصد دانلود شخص ثالث. روی سرور فعلی آن‌ها را دستی تغییر ندهید؛ تغییر نام در نسخه‌ای آینده به مهاجرت صریح نیاز دارد.

## نصب خودکار Cloudflare WARP و محافظت SSH

در Ubuntu/Debian، فایل `S1T-START.sh` اگر Cloudflare WARP نصب نباشد، بستهٔ رسمی را خودکار نصب می‌کند، کدنام توزیع را از سیستم تشخیص می‌دهد، مخزن رسمی Cloudflare را اضافه می‌کند و پروتکل MASQUE را تنظیم می‌کند. پیش از ثبت‌نام یا پیکربندی اولیه، تأیید صریح شرایط استفاده و حریم خصوصی Cloudflare از طریق ترمینال گرفته می‌شود. اگر تأیید نشود یا ترمینال تعاملی در دسترس نباشد، بسته نصب می‌شود اما ثبت‌نام/اتصال بدون اجازه انجام نمی‌شود. اگر به‌روزرسانی همهٔ مخازن APT به‌علت در دسترس نبودن Mirror میزبان شکست بخورد، نصب‌کننده به‌روزرسانی مخزن Cloudflare را به‌تنهایی هم امتحان می‌کند.

پیش از اتصال WARP، نصب‌کننده یک سرویس systemd و قوانین Policy Routing پایدار برای پاسخ‌های SSH می‌سازد؛ پورت SSH فعال و پورت‌هایی که `sshd -T` گزارش می‌کند از جدول اصلی شبکه عبور می‌کنند. پس از اتصال، مسیر پاسخ به SSH فعلی بررسی می‌شود. اگر نتوان آن را خارج از رابط/جدول WARP تأیید کرد، WARP برای جلوگیری از قفل‌شدن دسترسی مدیر قطع می‌شود. این محافظ مخصوص SSH است و تضمین نمی‌کند سرویس‌های مدیریتی دیگر مسیر قبلی خود را حفظ کنند. مسیر WARP در Shah Tunnel فقط وقتی قابل استفاده است که وضعیت `Connected` و `Network: healthy` باشد.

## نصب

روی Linux amd64 یا arm64 با systemd و دسترسی HTTPS به میزبان‌های دانلود رسمی Go، دستور را در پوشهٔ استخراج‌شدهٔ ZIP با کاربر root اجرا کنید:

```bash
sudo bash S1T-START.sh
```

وقتی ZIP را از حالت فشرده خارج کردید، از همان پوشه `sudo bash S1T-START.sh` را اجرا کنید تا دقیقاً همین سورس محلی ساخته شود. اجرای نسخهٔ یک‌خطی از GitHub، سورس شاخهٔ `main` منتشرشده را می‌گیرد و فقط پس از به‌روزرسانی آن شاخه شامل این اصلاحات خواهد بود. نصب‌کننده ابزار Go نسخهٔ `1.26.1` را ابتدا از آینه‌های منطقه‌ای و سپس از میزبان‌های رسمی دریافت می‌کند. اگر دانلود قطع شود، فایل ناقص هر آینه جداگانه نگهداری می‌شود و فقط از همان آینه، در صورت پشتیبانی HTTP Range، ادامه پیدا می‌کند؛ بنابراین داده‌های چند میزبان با هم مخلوط نمی‌شوند. پیش از استفاده، SHA-256 ثابت فایل بررسی می‌شود و آرشیو تأییدنشده پذیرفته نمی‌شود. اگر سورس محلی کنار اسکریپت باشد، همان نسخهٔ محلی ساخته می‌شود؛ در اجرای راه دورِ بدون سورس محلی، سورس شاخهٔ `main` دریافت می‌شود. سپس باینری متناسب با معماری با `CGO_ENABLED=0` ساخته می‌شود. هیچ باینری از GitHub Releases دانلود نمی‌شود و ابزار Go به‌صورت دائمی روی سرور نصب نمی‌شود. ابتدا Cloudflare WARP/MASQUE و محافظ مسیر مستقیم SSH آماده می‌شوند و سپس سورس و ابزار Go دانلود می‌شوند؛ اگر شرایط Cloudflare پذیرفته شده و WARP سالم متصل باشد، این دانلودها می‌توانند از مسیر WARP انجام شوند. اگر شرایط پذیرفته نشود یا WARP متصل نشود، نصب‌کننده در صورت امکان از مسیر معمول شبکه ادامه می‌دهد. قوانین محافظ SSH پیش از راه‌اندازی سرویس WARP نصب می‌شوند. سپس نسخه و معماری باینری ساخته‌شده بررسی می‌شود. از باینری قبلی نسخهٔ پشتیبان نگه داشته می‌شود و سرویس فعال برای جلوگیری از قطع اتصال‌های جاری ری‌استارت نمی‌شود. برای نصب مستقیم از GitHub پس از انتشار این اصلاحات در شاخهٔ `main`، می‌توانید از دستور یک‌خطی استفاده کنید: `bash <(curl -fsSL https://raw.githubusercontent.com/ShahNetLab/ShahTunnel/main/S1T-START.sh)`.

## ساخت و تست

برای اجرای اسکریپت تست، Go 1.26.1 باید از قبل روی سیستم موجود باشد؛ این اسکریپت ابزار Go را دانلود نمی‌کند. از ریشهٔ مخزن اجرا کنید:

```bash
./VERIFY-ALL-TRANSPORTS.sh
```

یا بررسی‌های اصلی را مستقیم اجرا کنید:

```bash
gofmt -w S1T-CAPSULE/main.go S1T-CAPSULE/main_test.go
go test -race -count=20 ./S1T-CAPSULE
go vet ./S1T-CAPSULE
mkdir -p dist
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags='-s -w -buildid=' -o dist/shah-tunnel-linux-amd64 ./S1T-CAPSULE
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags='-s -w -buildid=' -o dist/shah-tunnel-linux-arm64 ./S1T-CAPSULE
(cd dist && sha256sum shah-tunnel-linux-amd64 > shah-tunnel-linux-amd64.sha256)
(cd dist && sha256sum shah-tunnel-linux-arm64 > shah-tunnel-linux-arm64.sha256)
```
