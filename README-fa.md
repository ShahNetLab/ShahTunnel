## قابلیت‌ها

- **Adaptive با پنج مسیر در صورت پیکربندی REALITY:** ‏TCP/TLS، ‏WebSocket/TLS، ‏HTTP/2 CONNECT، ‏HTTP/1.1 CONNECT/TLS و REALITY روی listener جداگانه.
- **بازیابی خودکار:** اتصال مجدد با تأخیر افزایشی و jitter و ترجیح آخرین مسیر احراز هویت‌شدهٔ موفق برای هر lane.
- **امنیت:** TLS 1.3 در ارتباط خصوصی Hub↔Agent، احراز هویت توکن و تثبیت اثرانگشت SHA-256 گواهی.
- **هم‌زمانی:** دوازده lane مستقل به‌صورت پیش‌فرض، صف‌های محدود و انتخاب نشست با توجه به بار.
- **مدیریت:** منوی ترمینال، سرویس systemd، نمایش وضعیت و لاگ، نصب‌کننده و اسکریپت بررسی محلی.

## منوی انتقال

روی هر دو سمت Hub و Agent گزینهٔ سازگار را انتخاب کنید.

| گزینه | انتقال / راهبرد | عملکرد |
|---|---|---|
| `1` | TCP/TLS | جریان تونل روی اتصال TLS. |
| `2` | WebSocket/TLS | انتقال جریان در فریم‌های WebSocket داخل TLS. |
| `3` | HTTP/2 CONNECT | جریان CONNECT روی TLS و پورت TCP شمارهٔ کنترل + ۱. |
| `4` | HTTP/1.1 CONNECT/TLS | جریان CONNECT روی TLS و پورت TCP شمارهٔ کنترل + ۲. |
| `5` | HTTP CONNECT fallback | ابتدا HTTP/2 و در صورت شکست راه‌اندازی، HTTP/1.1 را امتحان می‌کند. |
| `6` | Automatic fallback | ابتدا TCP/TLS و سپس WebSocket/TLS. |
| `7` | Full Adaptive Failover | چهار مسیر قدیمی و در صورت تنظیم هر دو طرف، REALITY را نیز امتحان می‌کند؛ آخرین مسیر احراز‌شدهٔ موفق را برای هر lane ترجیح می‌دهد. |
| `8` | REALITY | دست‌دهی REALITY مبتنی بر TLS 1.3، احراز هویت کلید عمومی/Short ID و fallback به مقصد تنظیم‌شده برای اتصال‌های تأییدنشده. |

### پورت‌های فایروال Hub

اگر پورت کنترل Hub برابر `9443` باشد:

- `9443/TCP`: مسیرهای TCP/TLS و WebSocket/TLS.
- `9444/TCP`: ‏HTTP/2 CONNECT در گزینه‌های ۳، ۵ و ۷.
- `9445/TCP`: ‏HTTP/1.1 CONNECT در گزینه‌های ۴، ۵ و ۷.

فقط پورت‌های لازم برای گزینهٔ انتخاب‌شده را باز کنید. REALITY از TCP روی پورت کنترل استفاده می‌کند؛ برای این حالت، پورت‌های کنترل +۱ و +۲ لازم نیستند. در حالت Adaptive، REALITY در صورت تنظیم هر دو طرف به‌طور پیش‌فرض روی پورت کنترل +۳ گوش می‌دهد؛ برای کنترل `9443` یعنی `9446/TCP`. می‌توان آن را با `reality_listen` در Hub و `reality_addr` در Agent تغییر داد. حالت مستقل REALITY در گزینهٔ ۸ همچنان از همان آدرس کنترل استفاده می‌کند.

## تنظیم REALITY (گزینهٔ ۸ یا مسیر اختیاری Adaptive)

ابتدا Hub را با گزینهٔ ۸ تنظیم کنید. برنامه یک کلید خصوصی X25519 و یک کلید عمومی می‌سازد؛ فقط کلید عمومی، Short ID و SNI را در Agent وارد کنید. **کلید خصوصی فقط روی Hub می‌ماند.** پورت کنترل (به‌صورت پیش‌فرض `9443/TCP`) باید از Agent قابل دسترسی باشد.

`reality_sni` نام میزبان TLS است و `reality_dest` نشانی مقصد با قالب `host:port`؛ برای نمونه، SNI را نام دامنهٔ واقعی سایت پوششی و `reality_dest` را IP مبدأ همان سایت با قالب `host:port` قرار دهید؛ مقصد فقط وقتی می‌تواند با SNI متفاوت باشد که واقعاً همان نام را ارائه کند و مجاز به استفاده از آن باشید. مقصد باید از Hub قابل دسترسی و با SNI سازگار باشد؛ ترجیحاً یک سرویس واقعی با TLS 1.3 ارائه کند. انتخاب مقصد اشتباه ممکن است باعث شود handshakeهای fallback ناموفق باشند. اتصال‌های TLS تأییدنشده عمداً به همین مقصد ثابت هدایت می‌شوند تا پروب پاسخ واقعی سایت را دریافت کند؛ این رفتار پهنای باند خروجی مصرف می‌کند و مانند یک TCP proxy محدود به یک مقصد عمل می‌کند، پس مقصد را با دقت انتخاب کنید.

Agent از uTLS استفاده می‌کند و برای REALITY یکی از fingerprintهای `chrome`، `firefox`، `edge` یا `randomized` را می‌پذیرد. کلید عمومی و Short ID نقش تأیید REALITY را دارند؛ فیلد fingerprint گواهی SHA-256 مربوط به transportهای قدیمی در این حالت استفاده نمی‌شود. توکن ShahTunnel همچنان بعد از تأیید handshake لازم است.

> محدودهٔ این نسخه: تنظیمات REALITY در گزینهٔ Adaptive (گزینهٔ ۷) نیز پشتیبانی می‌شوند و در صورت تکمیل تنظیمات هر دو سمت، مسیر پنجم هستند. در حالت Adaptive، Hub به‌طور پیش‌فرض روی پورت کنترل + ۳ برای REALITY گوش می‌دهد؛ مسیرهای قدیمی روی پورت‌های قبلی می‌مانند. Agent از uTLS برای TCP/TLS، WebSocket/TLS، HTTP/2 CONNECT و HTTP/1.1 CONNECT استفاده می‌کند و pin گواهی SHA-256 را حفظ می‌کند؛ مقدار `tls_fingerprint` پروفایل `chrome`، `firefox`، `edge` یا `randomized` را تعیین می‌کند. QUIC/HTTP3، multipath هم‌زمان واقعی، انتقال یک جریان TCP باز به مسیر دیگر، و padding/morphing قابل تنظیم در این نسخه پیاده‌سازی نشده‌اند. Adaptive پس از قطع یک lane دوباره متصل می‌شود و مسیر بعدی را امتحان می‌کند؛ اتصال موجود را بدون وقفه به transport دیگر منتقل نمی‌کند.

## استفادهٔ مسئولانه و حریم خصوصی

ShahTunnel یک رلهٔ عمومی TCP است. آن را فقط برای سرورها و سرویس‌هایی پیکربندی کنید که مالک آن‌ها هستید یا مجوز صریح مدیریتشان را دارید. از آن برای دسترسی بدون مجوز به سامانه‌های اشخاص ثالث، انتقال ترافیک آزاردهنده یا مختل‌کردن سرویس‌ها استفاده نکنید. مسئولیت مقصدها و ترافیکی که عبور می‌دهید با مدیر سامانه است.

بخش نمایش اطلاعات سرور ممکن است برای تشخیص IPv4 عمومی و کشور سرور، درخواست HTTPS به سرویس‌های عمومی تشخیص IP و GeoIP از جمله ipify، icanhazip، checkip.amazonaws.com، ipinfo.io، ip.sb، ipapi.co و ipwho.is بفرستد. این سرویس‌ها می‌توانند IP عمومی سرور و فرادادهٔ درخواست را ببینند؛ درخواست‌های GeoIP شامل توکن تونل یا محتوای ترافیک تونل نیستند.

برای سازگاری هنگام ارتقا، نام واحد systemd و مسیر تنظیمات هنوز نام‌های قدیمی `ravanreverse.service` و `/etc/ravanreverse` را دارند؛ نصب‌کننده فرمان `shah-tunnel` را نیز به‌صورت symlink فراهم می‌کند. این‌ها نام‌های محلی برای سازگاری‌اند، نه مقصد دانلود شخص ثالث. روی سرور فعلی آن‌ها را دستی تغییر ندهید؛ تغییر نام در نسخه‌ای آینده به مهاجرت صریح نیاز دارد.

## نصب

روی Linux amd64 یا arm64 با systemd، با دسترسی HTTPS به میزبان‌های رسمی دانلود Go و مخزن سورس، دستور را با کاربر root اجرا کنید:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/ShahNetLab/ShahTunnel/main/S1T-START.sh)
```

حداقل نسخهٔ Go در go.mod برابر `1.27.0` است و نصب‌کننده از ابزار Go نسخهٔ `1.27.3` استفاده می‌کند. این نسخه با وابستگی فعلی REALITY که Go 1.27 یا بالاتر می‌خواهد سازگار است. نصب‌کننده ابزار Go نسخهٔ `1.27.3` را ابتدا از آینه‌های منطقه‌ای و سپس از میزبان‌های رسمی دریافت می‌کند. اگر دانلود قطع شود، فایل ناقص هر آینه جداگانه نگهداری می‌شود و فقط از همان آینه، در صورت پشتیبانی HTTP Range، ادامه پیدا می‌کند؛ بنابراین داده‌های چند میزبان با هم مخلوط نمی‌شوند. پیش از استفاده، SHA-256 ثابت فایل بررسی می‌شود و آرشیو تأییدنشده پذیرفته نمی‌شود. اگر نصب‌کننده را از پوشهٔ پروژهٔ استخراج‌شده یا clone اجرا کنید، همان سورس محلی ساخته می‌شود؛ اگر فرمان `bash <(curl ...)` را اجرا کنید، سورس شاخهٔ `main` مخزن دریافت می‌شود. سپس باینری متناسب با معماری با `CGO_ENABLED=0` ساخته می‌شود. هیچ باینری از GitHub Releases دانلود نمی‌شود؛ ابزار Go تأییدشده با SHA-256 در مسیر `/usr/local/lib/shah-tunnel/toolchains/` نگهداری می‌شود تا نصب‌های بعدی دوباره آن را دانلود نکنند. پیش از نصب، نسخه و معماری باینری ساخته‌شده بررسی می‌شود. از باینری قبلی نسخهٔ پشتیبان نگه داشته می‌شود و سرویس فعال برای جلوگیری از قطع اتصال‌های جاری ری‌استارت نمی‌شود.

## ساخت و تست

برای اجرای اسکریپت تست، Go 1.27.3 باید از قبل روی سیستم موجود باشد؛ این اسکریپت ابزار Go را دانلود نمی‌کند. از ریشهٔ مخزن اجرا کنید:

```bash
./VERIFY-ALL-TRANSPORTS.sh
```

یا بررسی‌های اصلی را مستقیم اجرا کنید:

```bash
gofmt -w S1T-CAPSULE/main.go S1T-CAPSULE/main_test.go S1T-CAPSULE/reality_transport.go
go mod tidy
go test -race -count=20 ./S1T-CAPSULE
go vet ./S1T-CAPSULE
mkdir -p dist
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags='-s -w -buildid=' -o dist/shah-tunnel-linux-amd64 ./S1T-CAPSULE
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags='-s -w -buildid=' -o dist/shah-tunnel-linux-arm64 ./S1T-CAPSULE
(cd dist && sha256sum shah-tunnel-linux-amd64 > shah-tunnel-linux-amd64.sha256)
(cd dist && sha256sum shah-tunnel-linux-arm64 > shah-tunnel-linux-arm64.sha256)
```
